# __tmpl_title

An IRIS mail-provider plugin: __tmpl_summary. Generated by
`iris plugin new __tmpl_name --kind mail-provider`.

| File | What it is |
|---|---|
| `src/__tmpl_package/plugin.py` | the `__tmpl_tool` provider (`MailProvider`) and `setup(api)` |
| `src/__tmpl_package/manifest.yaml` | the contract: `identity: provides: [email]` |
| `tests/test_plugin.py` | connect, sync, the identity source and the write gate, in a real IRIS |
| `tests/test_stable_tier.py` | the plugin imports only IRIS's stable tier |

A mail provider is written against one facade, `iris_personal.email.provider_api`: the
`MailProvider` interface and its types, `MailSyncStore` (what a sync writes),
`register_mail_provider`, `connect_account` and `mailbox_write` (with the
`WriteTally` it yields; `require_mailbox_writes` is its approval check alone). It needs the
email slice installed (`iris-harness[email]`).

## Try it

```bash
pip install -e ".[test]"
pytest
```

The tests need no network: the provider serves a fixed demo mailbox.

## Next

- Replace the demo mailbox with your service's API in `fetch_new` (keep it incremental:
  save a cursor with `store.set_cursor`) and `fetch_message_body`.
- Call `connect()` once you hold the account's credentials (in the vault), typically
  from your plugin's `iris` command (`cli:` in the manifest).
- Keep your connected addresses somewhere that survives a restart (beside the
  credentials) and return them from `owner_identity()`.
- Every method that changes the mailbox makes its write inside `mailbox_write`: the
  owner's approval is checked first, and what reached the mailbox (`tally.add(n)`) is
  recorded in the governance ledger after, where `iris governance proof-bundle check`
  finds it. The tests approve with `iris email writes approve`, as the owner would.
- Import only the stable tier; `tests/test_stable_tier.py` holds you to it.
