# __tmpl_title

An IRIS research-provider plugin: __tmpl_summary. Generated by
`iris plugin new __tmpl_name --kind research-provider`.

| File | What it is |
|---|---|
| `src/__tmpl_package/plugin.py` | the search `Backend` (a `SearchProvider`) and `setup(api)`, which registers it |
| `src/__tmpl_package/manifest.yaml` | the contract: name, entry point and the provider's name under `search_providers:` (a provider is not a tool, so no `tools:`) |
| `tests/test_plugin.py` | the search alone, then serving the `research` tool in a real, governed IRIS |
| `tests/model_script.yaml` | what the scripted model answers |
| `tests/test_stable_tier.py` | the plugin imports only IRIS's stable tier |

The backend joins the built-in `research` tool's provider chain
(`api.register_search_provider`): the model keeps calling `research`, and the chain tries
this provider after the configured built-ins and before the keyless DuckDuckGo floor. It
inherits the chain's guards (no question about the owner's own finances reaches it; their
name and email addresses are stripped from the query), its cache, rerank, injected-
instruction scan and audit. It serves wherever the `research` plugin is mounted (the
`default` profile).

## Try it

```bash
pip install -e ".[test]"
pytest
```

The tests need no network: the backend serves canned results.

## Next

- Replace `Backend.search` with your service's API. Return `[]` when it fails, never
  raise, and log each call with `iris_harness.sdk.logging.log_egress` (the host only).
- An API key is a setting: declare it under `settings:` in the manifest and check it in
  `is_available()` (read it there, not in `__init__`, so a key set later counts).
- The chain's order is `config/search_providers.yaml`: name `__tmpl_tool` there to move
  the provider, or pass `priority=` to `register_search_provider` (lower runs first).
- Import only the stable tier; `tests/test_stable_tier.py` holds you to it.
